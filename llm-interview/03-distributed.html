分布式训练与显存

从显存账出发，理解参数分片、矩阵并行、流水线与恢复。

各种并行缩写的共同问题是：哪部分工作太大，如何切开，切开后为了保持原来的数学计算要交换什么。先回答这三个问题，再选择框架和参数。

1. 先算一张显存账

对应面试题：P08、P15、I11。

以 7B 参数为例，假设 BF16 参数和梯度各占 2 字节，FP32 master weight 占 4 字节，Adam 两个 FP32 状态共占 8 字节，则总状态为每参数 16 字节，约 112 GB 十进制容量。若实现不保留独立 master copy、梯度使用不同精度或状态被分片，数字会不同。

这还不包含激活、Attention/KV 中间量、通信 buffer、重分片临时张量、CUDA Graph 内存池与 allocator 碎片。因此回答“7B 训练需要多少显存”，必须先声明精度、优化器、分片和 batch 假设。

Activation checkpointing 少保存部分前向激活，在 backward 时重算；它以额外计算换显存。Offload 把状态迁移到 CPU 等设备，以传输和调度开销换 GPU 空间。梯度累积通过多个小 micro-batch 得到较大的有效 batch，但模型状态仍需驻留；若通信未做相应处理，每个 micro-batch 都同步也会增加成本。

RL 中 rollout 能跑、actor update OOM，往往是因为推理阶段没有训练所需的激活和 optimizer 状态，进入更新时又需要参数 all-gather 或额外模型。应在阶段边界记录 allocated/reserved/peak，而不是只看作业刚启动的显存。PyTorch CUDA 内存说明

2. DDP、ZeRO 与 FSDP：复制和分片的取舍

对应面试题：P09、P10、E08、E09、E10。

DDP 的典型模式是每个 rank 持有模型副本、读取不同数据，在 backward 中同步梯度。设两个 rank 分别算出梯度 2 和 6，标准平均归约后都使用 4 更新。各 rank 必须以兼容顺序参加 collective，否则可能一直等待。

DDP 将梯度组织成 bucket，某 bucket 中的梯度就绪后即可发起通信，尝试与剩余 backward 重叠。Bucket 太小会增加启动次数；太大则等待更多参数就绪，延迟通信起点。因此要画梯度就绪与 collective 的时间线，不能只找一个“最优 MB 数”。动态未使用参数需要 reducer 知道哪些梯度不会产生；只有图结构满足相应约束时，才能使用 static graph 假设。DDP 设计

方案 跨数据并行 rank 分片的主要状态 主要影响
ZeRO-1 optimizer state 减少状态复制
ZeRO-2 再分片梯度 进一步降低常驻显存
ZeRO-3 再分片参数 需要按计算时机聚合参数

这里的“分片”不等于 offload；两者可组合。ZeRO-3 常驻参数更少，但某一层计算时仍可能需要完整参数或计算所需片段，峰值受聚合时机影响。ZeRO

FSDP 同样围绕参数、梯度和状态分片组织计算，但具体 API 和生命周期由实现决定。整模型作为一个很大的分片单元，聚合瞬间的峰值可能很高；逐层分片能缩短完整参数驻留时间，却增加通信调度次数。Prefetch 提高重叠，也可能让多组参数同时在显存中。解释时区分 FSDP1 wrapping 和 FSDP2 的 fully_shard，不要把版本接口混用。FSDP2 教程

3. TP 与 PP：切矩阵还是切层

对应面试题：P11、P12、P13。

考虑 MLP：Y = activation(XW₁)W₂。采用数学形状 W₁:[d,f]、W₂:[f,d]。列并行沿 W₁ 的输出维 f 切开，每个 rank 得到一部分中间通道；随后按 W₂ 的输入维 f 切开，各 rank 计算对完整输出的部分贡献，再归约求和。

rank 0: H₀=activation(X W₁,₀) → Y₀=H₀ W₂,₀
rank 1: H₁=activation(X W₁,₁) → Y₁=H₁ W₂,₁
最终 Y=Y₀+Y₁

因为激活函数逐元素计算，可以先在局部通道执行；若中间运算需要所有通道统计，通信需求会变化。实际库的 Linear 权重存储常为 [out,in]，需区分数学记号和张量存储。TP 往往在层内频繁通信，通常适合更快的互联，但不能把“TP 永不跨节点”当硬规则。Megatron-LM

PP 把不同层放到不同 stage，传递激活和反向梯度。填满、排空流水线时会产生 bubble。简单同耗时 stage 的 GPipe 式模型下，效率近似 m/(m+p−1)，m 是 micro-batch 数，p 是 stage 数；例如 p=4、m=4，近似效率为 4/7。真实 1F1B、交错调度、层不均衡和通信会改变该估计。GPipe

Megatron、DeepSpeed 不是与 TP/DP 并列的数学策略；它们是实现多种策略和训练组件的系统。选择时需要考虑模型支持、optimizer、checkpoint、推理权重转换与团队维护能力。

4. SP、CP、EP 与进程组不能机械相乘

对应面试题：P14、E11、E12。

Sequence Parallel 在不同框架里含义并不完全相同。Megatron 语境常指在部分非 TP 矩阵乘区域沿序列维分布激活；Context Parallel 则让长上下文在 Attention 计算中分布到多个设备。面试时先定义实际切的是哪段张量。

Ring 形式的 CP 可在各 rank 保留局部 query，并轮转 K/V 块；每轮处理一部分上下文。Ulysses 通过 all-to-all 在序列分片与 head 分片之间转换，允许局部执行 Attention，再转换回来。两者的通信次数、缓冲、head 数约束不同；GQA/MQA 下还要检查具体实现如何处理较少的 KV heads。DeepSpeed Ulysses

EP 把 expert 分到不同 rank，需要按路由 dispatch/combine token。EP 有时使用原本数据并行 mesh 内的某个轴，而非额外新增一维。因此“DP×TP×PP×EP”不一定等于总卡数。

一个白板例子：8 张卡可用 2 个 PP stage，每个 stage 有 4 个 rank。Dense 层按 TP=2、另一个轴做 DP；MoE 层可以重用其中某些 rank 组成专家组。正确描述是列出每层的 rank 集合和通信组，而不是不断乘缩写。共享轴的安排必须由框架支持，不能凭纸面设计自动成立。

5. 扩卡变慢与 NCCL hang 的排查

对应面试题：P17、P18、I14、E52。

All-reduce 使所有参与者得到归约结果；reduce-scatter 让各 rank 得到结果的一片；all-gather 拼齐各片；all-to-all 让各 rank 向其他 rank 交换不同数据。这些是语义，底层可以选择不同算法和传输路径。NCCL 集合通信

扩卡后 global batch 不变，会缩小每卡计算量，但 collective 启动与同步延迟未必同比下降。如果 global batch 增大，则每步时间可能更好看，却需要检查收敛和总 token 预算。至少分别报告吞吐、扩展效率和达到相同质量的时间。

Hang 先查最早失败的 rank，而非只看最终超时信息。比较最后一个 collective 的序号、shape、dtype、进程组；检查某个 rank 是否提前 OOM、异常退出或因空样本跳过 backward。只有控制流和输入一致后，才将重点放到链路、NIC、驱动和拥塞。

nccl-tests 正常只说明被测消息大小、拓扑和负载下的通信正常。训练中可能有不同 rank 布局、更小且密集的消息、CPU 调度延迟、GPU 计算争用或不同 NIC 亲和性。复现实验应尽量匹配真实 collective 的大小分布和并发情况。

6. Checkpoint 保存的是一个一致的训练时刻

对应面试题：E15、E16、I17。

同步 checkpoint 可以暂停更新后收集状态；异步 checkpoint 先将一个确定版本暂存到独立存储，再后台持久化。若后台线程一边读取 optimizer buffer，训练一边原地修改它，保存出来的内容可能混合两个时刻。“启动写入”不等于“已安全提交”。PyTorch 异步 checkpoint

可采用如下协议：分配 checkpoint ID → 暂存模型和 optimizer 等状态 → 各分片写临时对象 → 检查完整性 → 原子发布 manifest/完成标记。恢复只选择完整发布的版本。暂存会消耗额外 CPU/GPU 内存，因此同时允许几个在途任务必须有预算。

从 64 卡恢复到 32 卡，要按逻辑参数和状态重分片，而不是按原文件名假设原 rank 仍存在。Distributed Checkpoint 支持相关的重分片能力，但 optimizer 类型、参数命名及状态结构仍需兼容。PyTorch DCP

即使模型成功加载，样本顺序、有效 batch、随机数消费次序和归约顺序也可能变了。应分别承诺“可继续训练”“统计表现可复现”或“逐位相同”，并用恢复后的步数、样本 ID 和短程指标验证相应目标。
